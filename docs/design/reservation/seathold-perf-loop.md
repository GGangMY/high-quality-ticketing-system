# 좌석 선점 성능 개선 반복 기록 (2026-11-15~)

- 담당: 최권우 (좌석 선점)
- 관련: ISE-261, [배포 전 개선 측정](seathold-pre-deploy-measurements.md), [선점 구조 개선(ADR 0060)](seathold-structure-improvements.md)
- 진행 방식: 개선안 작성 → 다른 에이전트 세션의 독립 검토 → 적용 → 정합성 관문(전체 테스트, 동시성 C1~C7) → 변경 전·후를 같은 시점에 번갈아 측정 → 기록. 최대 5회 반복한다.
- 판정: p95, 좌석 조회 성공률, 동시 처리 요청 수(처리량), 실패율을 함께 본다. 정합성(중복 판매·불일치·유령 좌석)과 멱등성은 절대 조건이다. 차이가 측정 편차 안이면 "효과 없음"이다. 효과 없는 변경은 비용·위험이 있을 때만 되돌리고 근거를 적는다.

## 공통: 먼저 알아 둘 말
| 말 | 뜻 |
|---|---|
| 요청 기준 / 의도 기준 | 요청 기준은 서버가 받은 HTTP 요청 하나하나(재시도 포함)다. 의도 기준은 사용자 한 명이 "이 좌석을 잡고 싶다"고 누른 한 번이다. 프론트가 503·응답 없음에 같은 멱등키로 최대 3번 더 보내므로, 의도 하나가 요청 여러 개가 될 수 있다 |
| 의도 실패율 | 재시도까지 다 하고도 201(성공)이나 409(이미 잡힘)를 받지 못한 의도의 비율. 소비자가 실제로 겪는 실패다 |
| 의도 p95 | 처음 누른 때부터 마지막 결과를 받을 때까지 걸린 시간의 p95. 재시도 대기(1·2·4초)가 들어간다 |
| 동시 처리 상한 | 선점을 동시에 N개까지만 처리하고, 자리를 못 얻으면 커넥션을 잡기 전에 503으로 거절하는 장치(ADR 0060) |
| 유령 좌석 | 사용자는 실패(타임아웃)로 봤는데 서버가 뒤늦게 잡은 좌석 |
| 잠금 장애 | 인기 구역 20석을 측정 내내 잠근 느린 트랜잭션(관리 작업이 오래 걸리는 상황을 흉내 냄) |

## 측정 환경
한 PC(32코어)에서 Spring Boot 앱과 Docker PostgreSQL에 HTTP로 부하를 준다(`SeatHoldLoadTest`). 풀 5개, 커넥션 대기 1초, Tomcat 기본(작업 스레드 200). 부하는 열린 모델(1초에 N건, 응답과 상관없이)이고, 소비자 재시도 모사(`SEATHOLD_LOAD_CLIENT_RETRY=true`)를 켠다. 같은 코드도 측정마다 15%까지 흔들린다.

## 반복 1: 동시 처리 상한에 대기 인원 상한 (커밋 `92ba4a47`)

### 1-1. 기존 방식과 문제점
- 동시 처리 상한(ADR 0060)은 자리 4개가 차 있으면 최대 200ms 기다리고, 그래도 못 얻으면 503이다. 기다리는 요청 수에는 제한이 없었다.
- 기다리는 동안 요청은 Tomcat 작업 스레드(기본 200개)를 쥔다. 잠금 장애가 없는 1,800/s에서는 거의 모든 요청이 자리를 기다려 스레드가 바닥났다. 스레드를 못 받은 요청은 시한 없는 Tomcat 작업 대기열에 쌓여 3초 뒤 TIMEOUT을 맞았고, 같은 스레드를 쓰는 좌석 조회도 함께 실패했다([배포 전 측정](seathold-pre-deploy-measurements.md) 11절).
- 그 측정은 재시도가 없는 부하였다. 실제 프론트는 503·응답 없음에 같은 멱등키로 최대 3번 더 보낸다(약 1·2·4초 뒤). 503이 부하로 되돌아오는 효과가 빠져 있었다.

### 1-2. 바꾼 것
- **대기 인원 상한:** 자리를 기다리는 요청이 `seat-hold.max-concurrent-queue`(기본 64)명 이상이면 기다리지 않고 바로 503. 스레드 점유가 "자리 4 + 대기 64" 안으로 묶인다. 자리 대기 시간(200ms)과 자리 수(4)는 그대로다.
- **줄 순서 유지:** 자리를 바로 얻는 경로도 `tryAcquire(0, 단위)`로 써서 공정 세마포어의 줄 순서를 지킨다(시한 없는 `tryAcquire()`는 기다리는 요청을 건너뛴다).
- **거절 이유 지표:** `seathold.concurrency.rejected{reason=queue_full|wait_timeout}`. 대기 인원 초과는 몰림이 처리 한계를 넘은 것, 대기 시간 초과는 자리를 쥔 요청이 오래 걸린 것(잠금 장애 등)이다.
- **측정 도구:** 부하 테스트에 소비자 재시도 모사(`SEATHOLD_LOAD_CLIENT_RETRY`)와 의도 기준 지표를 더했다.

### 1-3. 예상
- 잠금 장애 없는 1,800/s: TIMEOUT이 거의 0, 좌석 조회 100% 근처. 다만 자리 4개의 처리 한계(약 1,800/s)에 닿아 TIMEOUT이 503으로 옮겨 갈 뿐일 수 있고, 재시도로 503이 늘 수 있다(검토 세션 지적).
- 잠금 장애 300/s: 지금과 같음. 600/s: 503 비율은 비슷하고 p95는 감소.

### 1-4. 실측 (조건마다 4회 평균, A·B·C·D → D·C·B·A 순서로 번갈아)

### 1-5. 결과가 이렇게 나온 이유
- **C가 B보다 TIMEOUT·유령·조회 실패를 없앤 이유:** 대기 인원이 64명으로 묶여 Tomcat 스레드가 바닥나지 않는다. 넘친 요청은 수 ms 안에 503을 받고 빠진다. 스레드가 남으니 좌석 조회도 바로 처리된다. 3초 동안 서버 안에 갇혀 있다가 뒤늦게 처리되는 요청이 없어 유령 좌석도 0이다.
- **C의 의도 실패율이 B보다 높은 경우(600/s 잠금 장애, 1,200/s)가 있는 이유:** B는 넘친 요청을 Tomcat 대기열에 3초까지 붙잡아 두었다가, 그중 일부를 늦게라도 처리했다(그 대가가 TIMEOUT, 유령, 조회 실패다). C는 그 요청을 바로 503으로 돌려보내고, 재시도 4번이 모두 몰림 구간에 걸리면 최종 실패가 된다. 1,200/s에서는 순간 몰림이 대기 인원 64명을 넘어 실패가 1.6% 생겼다.
- **정상 피크에서 상한을 끈 A가 가장 좋은 이유:** A는 커넥션 5개를 모두 선점에 쓰고, 상한은 4개만 쓴다. 처리 한계가 20% 낮다. 1,800/s는 자리 4개의 한계 근처라 C에서는 503 → 재시도가 다시 몰려(요청 기준 실패 53.8%, 평균 1.9번 시도) 11.3%가 끝내 실패했다. A는 그 부하를 커넥션 대기로 흡수했다.
- **잠금 장애에서 A가 무너지는 이유:** 잠긴 좌석을 노린 요청이 50ms씩 커넥션을 쥐어 처리 한계가 초당 수백 건으로 떨어진다. 재시도까지 몰려 3초 타임아웃이 쌓이고, 유령 좌석 216석, 좌석 조회 성공 20%다. 상한은 이 상황을 막으려고 있다.
- **가상 스레드(D)를 채택하지 않은 이유:** 스레드 고갈이 없어져 C와 비슷한 결과였지만 나은 점이 없다(1,800/s 의도 실패 14.7% 대 C 11.3%, p95 208 대 54ms). 서비스 전체(다른 담당 모듈 포함)의 실행 방식을 바꾸는 변경이라 위험에 견줘 얻는 것이 없다.

### 1-6. 판정
- **C 유지.** 상한을 켰을 때의 실패 모양이 "3초 TIMEOUT·유령 좌석·조회 실패"에서 "빠른 503 + 재시도"로 바뀌었다. 정상 1,800/s에서는 의도 실패도 19.7% → 11.3%로 줄었다.
- **남은 문제(다음 반복):** 상한 4개가 커넥션 5개보다 좁아 정상 피크에서 처리 한계를 20% 깎는다. 1,200/s에서도 대기 인원 64명이 순간 몰림에 넘친다.
