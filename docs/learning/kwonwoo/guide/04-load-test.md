# 부하 테스트 종류와 측정 결과

목차: [README](README.md)

2026-11-18 기준이다. 측정은 두 곳에서 했다. local(개인 노트북의 Docker)은 병목을 하나씩 찾는 단계 측정에, 배포 서버(EC2 m7i.xlarge, 4 vCPU)는 실제 운영 조건의 판정에 썼다. 두 결과가 다를 때는 배포 서버를 따른다. 그 이유는 6절에 있다.

## 1. 부하 테스트 종류

> 비유: 다리 안전 검사. 차 몇 대로 다리가 서 있는지 보고(smoke), 평소 교통량을 올리고(load), 다리가 휘어질 때까지 늘리고(stress), 갑자기 차 수천 대를 한꺼번에 올리고(spike), 하루 종일 차를 올려 둔다(soak). 차를 내린 뒤 다리가 원래대로 돌아오는지도 본다(recovery).

| 유형 | 묻는 질문 | 이 프로젝트의 시나리오 |
|---|---|---|
| Smoke | 돌아가기는 하나 | 발생기 연결 확인(VU 2·20초) |
| Load | 예상 부하에서 목표를 지키나 | K1(L), S1, B1-d, X1, L3 |
| Stress | 어디서 무너지나 | K1(S), K1-H, G1, B1, PAY1, R1, L1 |
| Spike | 순간 폭주를 받나 | Q1(초당 3,000), Q1-d(1초 버스트), A0(동시 100명 × 10회) |
| Soak | 오래 버티나 | 전용 스크립트 없음. 가장 긴 것은 O1 25분 |
| Recovery | 부하가 끝나면 돌아오나 | K1(S) 회복 탐침, B8 |

### 부하 모델: 열린 모델과 닫힌 모델

> 비유: 닫힌 모델은 손님 100명이 각자 음식을 받아야 다음 주문을 한다. 가게가 느려지면 주문도 줄어 문제가 가려진다. 열린 모델은 손님이 가게 사정과 상관없이 초당 100명씩 들어온다. 실제 티켓 오픈은 열린 모델이다.

그래서 대부분 `constant-arrival-rate`, `ramping-arrival-rate`(도착률 고정·증가)를 쓴다. 가상 사용자(VU)가 모자라 못 보낸 요청은 `dropped_iterations`로 남아, 서버가 아니라 발생기가 한계인지 판단하는 근거가 된다. 이 문서의 "초당 100명"은 1초에 새로 들어오는 사용자 수(도착률)이고 동시 접속자 수가 아니다.

### 왜 좌석 선점에서 spike와 soak를 뺐나

대기열이 입장을 일정 속도로 퍼뜨리므로 좌석 선점에는 스파이크가 오지 않는다. 오픈 순간의 폭주는 대기열 진입(Q1)이 받는다. soak는 좌석이 수 분 안에 다 팔려 의미가 없고, 그 뒤 선점 만료는 X1이 본다(`docs/design/reservation/k6-seathold-bottleneck-plan.md` 1-6절).

## 2. 도구와 환경

- k6: Docker `grafana/k6:1.0.0`. 요약 JSON과 원자료 CSV를 남긴다.
- 배포 측정: 같은 VPC의 발생기 EC2(c6i.xlarge)에서 Gateway 사설 IP로 보낸다. 한 번에 한 명만 쓰고, 시작·끝에 측정 모드를 켜고 끄면 슬랙에 알림이 간다([`docs/guides/loadgen.md`](../../../guides/loadgen.md)).
- 지표: Prometheus가 5초마다 앱 8개를 수집하고, k6 결과도 remote write로 보낸다(ADR 0046). Grafana 대시보드는 개발 기반, 대기열, 좌석 선점, 결제, 추첨, 요청 로그가 있다.
- 매회 대사 SQL로 중복 판매와 매수 불일치를 확인했다. 위반이 나온 회는 처리량을 쓰지 않는다. 지금까지 모든 회에서 위반은 0이다.
- 측정·시연 시드는 1,500석이다(ADR 0060). 그전 회차는 15,000석이라 문서마다 좌석 수가 다르니 함께 본다.

## 3. local 단계 측정: 좌석 조회 병목을 하나씩 걷어낸 과정 (ISE-79)

> 비유: 막힌 하수관을 뚫는 일. 한 곳을 뚫으면 물이 다음 막힌 곳까지 가서 또 막힌다. 그래서 한 번에 하나씩 고치고 매번 다시 잰다.

K1은 대기열 입장 직후의 사용자 흐름이다. 초당 100명이 5분 동안 들어와 좌석 조회 → 1~3초 고민 → 1~2석 선점을 하고, 이미 잡힌 좌석이면 다시 조회해 최대 2번 더 시도한다. 회차 하나 15,000석, 70%가 앞 구역 10% 좌석을 고른다. 정본은 [`k6-seathold-story.md`](../../../design/reservation/k6-seathold-story.md)다.

진행 원칙은 다섯 가지였다. 수정하지 않은 코드(base)에서 시작한다. 직면한 병목 하나만 고치고 다시 잰다. 측정 전에 예상을 적는다. 한 단계는 측정 브랜치 커밋 하나다. 기준선과 최종만 3회 반복한다.

| 단계 | 직면한 문제 | 해결 | 좌석 조회 성공(L) | 버틴 단계(S) |
|---|---|---|---|---|
| base | 컨테이너 메모리가 작아 JVM이 Serial GC를 골라 부하 시간의 약 75%를 GC로 멈춤 | - | 0.13% | 10명, 회복 실패 |
| G1 | GC 정지는 7%로 줄고 커넥션 대기 197건이 드러남 | `-XX:+UseG1GC` 명시 | 0.7% | 20명, 회복 실패 |
| R1 | 대기 초과 500이 28,613건. 조회 한 건이 엔티티 3만 개를 만들며 커넥션을 오래 쥠 | 커넥션 대기 시한 30초 → 1초 | 40.3% | 20명, 40초 뒤 회복 |
| P4a | PostgreSQL CPU 약 4.3코어, 커넥션 5개가 15,000행 조인에 묶임 | 엔티티 대신 필요한 열만 DTO로 읽기 | 81.3% | 80명, 30초 뒤 회복 |
| P4b | 640~1,280명 사이에서 커넥션 대기 | 바뀌지 않는 좌석 배치(구역·열·번호·등급·가격)를 회차마다 한 번 만들어 서비스 메모리에 캐시 | 100%(p95 11ms) | 640명 |
| P4c | 남은 비용은 응답 생성·JSON 직렬화(약 57%) | 좌석 상태를 1초 동안 공유 캐시 | 100%(p95 7ms) | 1,280명 |

병목은 JVM 메모리(GC) → 커넥션 대기 → DB 조인 → 응답 직렬화 순서로 옮겨 갔다.

- R1이 왜 효과가 있나: Gateway는 3초에 포기하는데 서버는 커넥션을 30초까지 기다리며 이미 버려진 요청을 계속 처리했다. 빨리 실패시키면 줄이 비워지고 커넥션이 성공할 요청으로 돌아간다. 이 값은 운영 설정에 반영됐고(ISE-196), 대기 초과는 500이 아니라 503으로 답한다(ISE-293).
- P4c의 1초 낡은 상태가 괜찮은 이유: 낡은 상태로 이미 잡힌 좌석을 골라도 선점 UPDATE가 DB에서 최종 판정하므로 중복 판매는 생기지 않는다. 409 비율은 76.6%에서 76.9%로 거의 같았다.
- 배치를 Redis가 아니라 서비스 메모리에 둔 이유(ADR 0054): 같은 조건에서 Redis에 두자 요청마다 1.3MB를 옮겨 역직렬화하느라 p95가 7.0ms에서 38.3ms로, 한 건당 CPU가 약 4.5배로 늘었다. 배치는 공연 중 바뀌지 않으므로 서버마다 따로 들고 있어도 어긋날 일이 없다.

### 최종 비교 (base와 F, 각 3회)

F는 P4c에 정합성 수정 S1~S4, G1·R1, 풀 10을 더한 조합이다.

| 측정 | base | F |
|---|---|---|
| K1 L 좌석 조회 성공 | 0.13% | 100% |
| K1 L 매진 전 p95(조회·선점) | 거의 모두 3초 초과 | 7ms·8ms |
| K1 L 선점 성공 | 0건, 매진 안 됨 | 약 10,100건, 189초에 매진 |
| K1 S GC 정지 비율 | 약 76% | 1% 안팎 |
| K1-H 800명 선점 p95/p99 | 27/40ms | 11/16ms |

주의할 점이 있다. 640명·1,280명 단계는 매진 뒤라 좌석 조회만 왔다. 조회와 선점이 섞인 부하로 확인한 한계는 320명이다. 4코어로 CPU를 묶으면 160명에서 느려지고 320명에서 실패가 시작된다. local 결과는 상대 비교로만 쓴다.

### 넣지 않은 단계

"직면하지 않은 병목은 미리 고치지 않는다"를 따랐다. 예를 들어 DB 왕복 줄이기(P3)는 선점 경로 800명에서도 커넥션 대기 0, p95 3ms라 넣지 않았다. Redis로 잡힌 좌석을 먼저 거절하는 안(P5)은 좌석 상태를 두 곳에 두는 복잡도가 커서 넣지 않았다.

## 4. 동시성 결함과 정합성 수정

k6 사용자는 요청을 하나씩만 보내 아래 결함을 직면하지 않는다. 그래서 JUnit 동시성 테스트(C1~C7)로 찾고 고쳤다(TS-65~68, PR #458).

| 결함 | 수정 | 고치기 전 → 고친 뒤 |
|---|---|---|
| 같은 사용자가 탭 4개로 8매 선점 | 매수 검사와 반영을 조건부 UPDATE 한 문장으로 | 한도 초과 30라운드 → 0 |
| 같은 멱등키 연타에 자기끼리 409 | 멱등키 행을 가장 먼저 기록 | 60건 → 0 |
| 잠긴 좌석을 끝없이 기다림 | `lock_timeout`(500ms → 50ms), 좌석 ID 순서로 잠금 | 최대 대기 2,215ms → 171~225ms |
| 만료 스케줄러끼리 헛수고 | `FOR UPDATE SKIP LOCKED` | 100건 → 0 |

수정 뒤 K1-H 선점 p95는 넣기 전과 같았다(400명까지 5ms 이하). 정합성 수정은 측정 가능한 성능 비용 없이 들어갔다.

## 5. 배포 서버 측정

### 5-1. Gateway 과부하 (G1: 대기열 순번 조회, 11/9~11/12)

Gateway가 메모리 768MiB에서 세 번 죽었다. 메모리만 늘리자 2,000/s p95가 435ms에서 752ms로 오히려 느려졌다(TS-58). 동시에 처리하는 요청 수에 상한이 없어 요청이 쌓이는 만큼 메모리와 지연이 같이 늘었던 것이다.

| 개선 | 지표 | 전 | 후 |
|---|---|---|---|
| 동시 처리 상한 500 → 64 | 2,000/s 성공 처리량 / p95 | 1,304/s / 571ms | 1,696/s / 87ms |
| 거절 지점을 HttpHandler 앞단으로(H1) | 2,500/s 성공 처리량 / p95 | 1,608/s / 104ms | 1,814/s / 78ms |
| 요청 로그를 문제 요청만(H2, ADR 0052) | 1,000/s CPU, 2,500/s 성공 처리량 | 78%, 1,814/s | 66%, 2,122/s |

64는 리틀의 법칙(동시 요청 수 = 처리량 × 처리 시간)으로 계산한 값이다. 구현 세션이 낸 500과 6차 측정의 128 안은 거부했다. 같은 장비에서 2,500/s 성공 처리량이 1,608에서 2,122/s가 됐다(`docs/presentation/performance/2026-11-14-gateway-overload-one-page.md`).

### 5-2. 좌석 조회 (S1, 15,000석 회차)

| 단계 | 실패 0으로 버틴 최대 초당 요청 |
|---|---|
| 개선 전 | 5 |
| P4a(DTO) | 40 |
| P4b(배치 캐시) | 100 |
| P4c(1초 상태 캐시) | 200 |

남은 한도는 초당 약 295건이고, 응답(약 820KB) 생성·전달 CPU가 한계였다.

### 5-3. 결제와 추첨

- PAY1(11/12): PG 허가 10, PG 지연 300ms에서 승인이 초당 약 31건에 멈추고 80/s에서 503이 59.5%였다. 허가 30이면 91.5/s, 거절 0.2%라 30으로 올렸다. PG 호출이 트랜잭션 밖이라 허가를 늘려도 DB 커넥션은 최대 3개만 썼다.
- 추첨 자동결제 L2-a: 10분 안 완료율이 92~93%(초당 약 3.2건)에서 소비자 3개·전용 PG 허가 그룹 뒤 100%(초당 약 9.4건)가 됐다(ADR 0051). 일반 결제 503은 9.5%에서 0이 됐다.

### 5-4. 섞인 흐름 O1 (사용자 3,000명)

개선 묶음(요청 로그 축소, JIT 예열, 좌석 응답·공연 상세 1초 캐시, 선점 사전 거절) 전후로 각 2회 쟀다. 확정 예매가 평균 10.7% 늘고 선점 p95가 242.7·196ms에서 44.5·31.4ms로 줄었다. LLM으로 만든 가상 사용자(Synthetic)는 균일 사용자보다 409 비율이 낮았다(11.7% 대 49.8%). 실제 사용자는 좌석을 골고루 고르지 않는다는 것을 숫자로 보여 준 비교다.

### 5-5. 좌석 선점 세 방식 비교 (ISE-296, 11/16·11/17)

동기형, 접수형 Outbox, 접수형 직접 발행을 같은 장비에서 쟀다. Gateway 상한은 끄고 쟀다. A0는 동시 100명 × 10회 몰림, K1-H는 초당 20 → 320 램프다. 정본은 [`deploy-seathold-steps-results.md`](../../../design/reservation/deploy-seathold-steps-results.md)다.

| 단계 | 설정 | A0 성공률 | A0 성공 처리량 |
|---|---|---|---|
| S0 | 동기형, 사전 거절 끔 | 99.2% | 580건/초 |
| S1 | 동기형, 사전 거절 켬 | 98.8% | 521건/초 |
| S2 | 동기형, 선점 동시 처리 상한 4 | 41.7% | 323건/초 |
| P8 | 상한 7, 풀 8 | 55.6% | 361건/초 |
| O | 접수형 Outbox, 상한 4 | 53.3% | 499건/초(202) |
| D | 접수형 직접 발행, 상한 4 | 55.8% | 485건/초(202) |

- K1-H에서 동기형(S0·S1)은 약 10만 7천 건 중 실패 0, 성공 p95 7.8~10.5ms였다. 320/s로는 동기형의 한계를 찾지 못했다.
- 커넥션 대기는 A0 몰림에서만 생겼고(최대 95, 획득 최대 0.76초) 대기 시한 초과는 0건이었다. 실패는 커넥션이 아니라 상한의 503에서 났다.
- 접수형 Outbox는 접수의 66%가 30초 시한으로 거절됐다. Outbox 릴레이가 같은 키를 한 번에 1건씩만 보내 구역 키 하나가 초당 약 2건에 묶였다. Kafka lag는 0~2라 Kafka-UI만 보면 문제가 보이지 않았고, 대기는 Kafka 앞 Outbox 테이블에 최대 1,941건 쌓였다.
- 결론: 운영은 동기형, 선점 동시 처리 상한은 끔, 커넥션 풀 5 유지(ADR 0062 11/17 갱신, ADR 0064). 이유는 [08 지금 방식이 합리적인 이유](08-why-current-design.md) 3절에 있다.

## 6. 측정에서 배운 것

- 내가 잰 것이 서버인가부터 본다. k6 메모리 상한(2.5GiB)에 닿은 k6가 GC로 멈췄다 요청을 몰아 보내, 한때 "1,280명 한계는 Gateway와 발생기"로 잘못 판단했다. 상한을 6GiB로 올리자 같은 코드가 100%를 처리했다(TS-69). Docker 포트 전달이 처리량을 약 40% 깎은 적도 있어 k6를 compose 네트워크에 붙였다.
- local 결론을 배포에서 다시 확인한다. local은 DB가 쓸 CPU가 넉넉해 배포 장비의 CPU 포화를 재현하지 못한다. 실제로 두 번 뒤집혔다. local에서 풀 10이 좋았지만 배포에서는 풀 5에서 대기 0이었다(ADR 0064). local에서 선점 동시 처리 상한이 타임아웃을 0%로 만들었지만 배포에서는 503만 늘렸다(ADR 0062).
- 화면 하나로 결론 내리지 않는다. Kafka-UI의 lag가 작아도 병목은 Kafka 앞(Outbox)에 있을 수 있다.
- 이름이 겹친다. local 단계의 "G1"은 G1 GC이고, 배포 시나리오 "G1"은 Gateway 순번 조회다. "S1"도 좌석 조회 시나리오, ISE-296 단계, 동시성 수정 세 가지 뜻으로 쓰였다. 문서를 읽을 때 어느 S1인지 먼저 본다.

## 7. 진행 현황

| 유형 | 측정함 | 남은 일 |
|---|---|---|
| Smoke | 측정 날마다 발생기 → 배포 Gateway 연결 확인 | - |
| Load | local K1(L) base~F, 배포 S1·O1 | - |
| Stress | local K1(S)·K1-H, 배포 G1·PAY1·K1-H 320/s | 동기형 선점의 배포 한계(320/s 위) |
| Spike | 배포 Q1, A0 | - |
| Recovery | local B8 | 배포 환경 재확인 |
| Soak | 없음 | O1 25분이 가장 김 |
| 전체 흐름 | 배포 O1 3,000명(균일·Synthetic) | - |

재지 않은 조합: 풀 8 + 상한 없음, 응모·추첨 실행·접수형 소비자가 겹치는 조합(ADR 0064 "재지 않은 것"). 접수형 Outbox의 키당 순차 발행은 공통 모듈 설계라 사실만 기록하고 고치지 않았다.

## 면접 포인트

- "부하 테스트에서 찾은 병목과 개선 수치" → 좌석 조회가 GC(Serial)에서 시작해 커넥션 대기, DB 조인, 직렬화 순서로 막혔다. 하나씩 고쳐 local 성공률 0.13%→100%, 배포 서버에서 실패 없이 버틴 좌석 조회가 초당 5건→200건이 됐다.
- "커넥션 풀을 늘리면 되지 않나" → 배포 장비에서 풀을 10으로 올리자 500은 사라졌지만 커넥션을 쥐는 시간이 두 배가 되고 선점 p95가 1.06초에서 1.83초로 나빠졌다(1회 측정). DB CPU가 먼저 차면 동시 쿼리만 늘어 다 같이 느려진다. 오래 쥐는 쿼리가 있으면 풀보다 쿼리를 고친다(자동 배정 인덱스 사례).
- "부하 테스트 결과를 어떻게 믿나" → `dropped_iterations`, k6 메모리, 발생기 지연 지표로 발생기 한계를 먼저 걸러 내고, 매회 대사 위반 0을 함께 확인했다. 발표 비교점은 3회 반복했다.
