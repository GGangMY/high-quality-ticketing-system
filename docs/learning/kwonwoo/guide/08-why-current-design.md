# 지금 방식이 합리적인 이유

목차: [README](README.md)

이 프로젝트의 핵심 질문 여덟 개에 대해 지금 방식, 검토한 대안, 지금 방식을 고른 근거, 감수하는 대가와 다시 볼 조건을 적는다. "합리적"의 기준은 세 가지다. 측정이나 사고로 확인한 근거가 있는가, 대안의 비용을 비교했는가, 바꿀 조건을 미리 정했는가. 근거가 약한 곳은 약하다고 적었다.

## 1. 서비스는 왜 셋(user·reservation·payment)인가

- 지금: 업무 서비스 셋. 대기열·좌석·예매·추첨은 reservation 안의 모듈이다.
- 대안: 대기열·추첨까지 나눈 5개(SA 처음 안). AI 교차 검토는 대기열 분리를 권했다.
- 근거: 나누는 기준을 "함께 바뀌어야 하는 데이터"와 "떼어 냈을 때 장애가 격리되는가"로 잡았다. 추첨 당첨 선점은 일반 선점과 같은 좌석 행을 한 트랜잭션에서 바꾼다. 나누면 분산 트랜잭션이 된다. 대기열은 Redis 카운터뿐이고 멈추면 예매도 멈춰, 떼어 내도 장애가 격리되지 않는다.
- 대가: reservation 한 서비스에 트래픽이 몰린다. 풀 5개를 좌석 조회·선점·추첨·스케줄러가 나눠 쓴다.
- 다시 볼 조건: 추첨 실행이 일반 선점을 늦춘다는 측정(L3: 선점 p95 11.06 → 21.0ms, 기준 20% 초과, 1회)이 반복되면 추첨 분리를 검토한다. 아직 결정하지 않았다.

## 2. 오픈 폭주는 왜 대기열로 받나

- 지금: Redis Lua로 순번(seq)을 주고 초당 50명씩 `admitted`를 올린다. 차례가 온 사람만 10분짜리 입장 토큰을 받는다.
- 대안: 모두를 좌석 서비스로 바로 보내고 서버를 늘리기, Gateway에서 사용자별 요청 제한.
- 근거: 좌석은 한정 자원이라 서버를 늘려도 "누가 먼저인가"는 한 곳에서 정해야 한다. 대기열이 앞에서 받으면 좌석 서비스에는 일정 속도만 들어오고, 이 속도는 측정한 좌석 서비스 한계에 맞춰 정할 수 있다. Lua 한 번으로 순번 부여와 READY 판정을 원자적으로 해서 인스턴스가 몇 대든 같은 결과를 낸다(`lastTick`으로 같은 초 중복 입장도 막음).
- 대가: 50명은 기준선 측정 전에 둔 임시값이다(SA 3-3). 측정에서는 그 두 배인 100명을 견디는 것을 확인했고, local 단계 측정의 섞인 부하 한계는 320명이다. 운영값을 측정 결과로 다시 정하지는 않았다.
- 한계: Redis가 한 대라 대기열 Redis가 죽으면 진입은 503이다(차단기 + Retry-After). 사용자별 요청 제한은 없다.

## 3. 좌석 선점은 왜 지금 모양인가

> 비유: 좌석 하나를 두고 다투는 일의 최종 심판은 DB다. 앞의 장치들은 심판에게 가는 줄을 짧게 만들 뿐, 심판을 대신하지 않는다.

### 3-1. 왜 DB 조건부 UPDATE이고 분산락·Redis 선점이 아닌가

- 지금: `UPDATE ... WHERE status = 'AVAILABLE'` 조건부 UPDATE, 부분 유니크 인덱스, 좌석 ID 오름차순 잠금.
- 대안: Redis 분산락, Redis에 좌석 상태를 두고 먼저 선점.
- 근거: DB 제약만으로 "한 좌석은 한 명"이 보장된다. 분산락을 더하면 같은 보장을 두 번 하고, 락 만료나 Redis 지연이 선점 경로 전체를 막을 수 있다. Redis 선점은 좌석 상태를 두 곳에 두어 둘이 어긋날 때 무엇이 맞는지 정하는 일이 생긴다. 측정에서도 DB가 한계가 아니었다: 배포 서버 K1-H 초당 320건에서 동기형 실패 0, p95 7.8~10.5ms였다.
- 근거 보강: 모든 측정 회차에서 중복 판매·매수 불일치 대사 위반은 0이다.

### 3-2. 왜 동기형이고 접수형(Kafka)이 아닌가

- 지금: 운영은 동기형(`seat-hold.mode: sync`). 접수형은 구현해 두고 비교 측정에 썼다.
- 대안: 접수형. 요청을 Kafka에 넣고 202를 준 뒤 소비자가 처리한다. SA에서 비교 대상으로 설계했다.
- 근거(ISE-296, 같은 배포 장비):

| 방식 | A0(동시 100명 몰림) 성공률 | 성공 처리량 | 처리 시작까지(K1-H) |
|---|---|---|---|
| 동기형, 상한 끔(S1) | 98.8% | 521건/초 | 즉시(응답 p95 10.5ms) |
| 동기형, 상한 4(S2) | 41.7% | 323건/초 | 즉시 |
| 접수형 Outbox, 상한 4(O) | 53.3% | 499건/초(202) | p95 25.5초, 접수의 66%가 30초 시한으로 거절(O2) |
| 접수형 직접 발행, 상한 4(D) | 55.8% | 485건/초(202) | 0.1초 이하(몰림 때 2.8초) |

- 해석: 접수형은 같은 상한 조건의 동기형보다 성공률이 조금 높지만, 상한을 끈 동기형보다 낮다. 사용자는 202를 받고도 결과를 폴링해야 한다. Outbox 경로는 릴레이가 같은 키를 한 번에 1건씩 보내 인기 구역 키 하나가 초당 약 2건에 묶였다. Kafka lag는 0~2였고 대기는 Kafka 앞 Outbox 테이블(최대 1,941건)에 쌓였다.
- 대가: 동기형은 몰림이 커지면 DB 커넥션 대기가 생긴다(A0에서 최대 95, 획득 최대 0.76초). 대기 시한 1초 초과는 0건이었다.
- 다시 볼 조건: 동기형이 커넥션 대기 시한을 넘겨 503을 내기 시작할 때. 이때 접수형을 다시 본다면 Outbox의 키당 순차 발행(공통 모듈 설계)부터 고쳐야 한다.

### 3-3. 왜 잠금 대기 50ms인가

- 지금: `lock_timeout 50ms`, `FOR UPDATE`는 유지.
- 대안: 500ms(SA 원안), `SKIP LOCKED`(AI 첫 추천), `NOWAIT`.
- 근거: 잠긴 좌석을 기다리는 요청은 그동안 커넥션을 쥔다. 500ms면 초당 약 20건부터 커넥션 대기가 번진다(계산). SKIP LOCKED는 곧 롤백될 요청이 잠깐 쥔 잠금까지 건너뛰어 실제로는 잡을 수 있던 좌석을 409로 돌려보냈다. 동시성 시나리오 C2 성공이 83에서 56으로 줄었다. 50ms는 C2 성공을 78~92로 유지하면서 최대 대기를 643ms에서 171~225ms로 줄였다(ADR 0061, TS-73).
- 대가: 50ms 안에 못 얻으면 실제로는 곧 풀릴 잠금이어도 409다. 좌석 경합에서는 어차피 한 명만 이기므로 빨리 알려 다른 좌석을 고르게 하는 편이 낫다고 봤다.

### 3-4. 왜 먼저 거절하나

- 지금: 1초 캐시로 잡힌 좌석을 쓰기 전에 거절하고, 쓰기 트랜잭션 안에서도 쿼리 한 번으로 판정한 뒤 잡을 수 없으면 아무것도 쓰지 않는다.
- 근거: 오픈 부하에서 선점 응답의 77~97%가 409였다. 지는 요청이 쓰기를 하고 잠금을 잡지 않게 하면 이기는 요청의 줄이 짧아진다. local에서 처리량이 65% 늘고 p95가 198ms에서 124ms로 줄었다(ADR 0062).
- 대가: 캐시는 최대 1초 낡을 수 있다. 낡은 캐시가 "비어 있음"이라 해도 최종 판정은 DB UPDATE가 하므로 중복 판매는 생기지 않는다. 배포에서는 켜고 끈 차이가 409 p95 0.4ms로 작았다. 효과가 작아도 해가 없어 켜 둔다.

### 3-5. 왜 동시 처리 상한을 만들어 놓고 끄나

- 지금: `seat-hold.max-concurrent`는 코드에 있고 운영 값은 0(끔)이다. 비상 스위치로 남긴다.
- local 근거(켜자는 쪽): 600/s에서 타임아웃 57~76% → 0%, 좌석 조회 성공 29~47% → 100%, 유령 선점 0석.
- 배포 근거(끄자는 쪽): 상한 4를 켜면 A0 성공률이 98.8%에서 41.7%로, 처리량이 521에서 323건/초로 떨어졌다. 실패는 커넥션 대기가 아니라 상한이 낸 503이었다.
- 왜 결과가 갈렸나: local은 DB가 쓸 CPU가 넉넉해 잠긴 좌석 대기가 풀을 오래 쥐는 상황이 주 문제였다. 배포에서는 잠금 대기를 50ms로 줄이고 먼저 거절을 넣은 뒤라 커넥션 대기가 실패로 이어지지 않았다. 고칠 문제가 이미 다른 장치로 사라진 자리에서 상한은 대가(503)만 냈다.
- 다시 볼 조건: 커넥션 대기가 다시 주 병목일 때. 켠다면 상한은 풀보다 작아야 보호가 되므로 상한 7이면 풀 8을 함께 올린다(ADR 0064 11/17 확인).

### 3-6. 왜 커넥션 풀이 5인가

- 지금: reservation 풀 5, 대기 시한 1초, 초과는 503.
- 대안: 10(local K1-H에서 p95 14ms → 3ms).
- 근거: 배포 장비에서 풀 10은 500을 없앴지만 커넥션을 쥐는 시간이 16.5ms에서 33.2ms로 두 배가 되고 선점 p95가 1.06초에서 1.83초로 나빠졌다(1회, 방향만 읽음). DB CPU가 먼저 차면 동시 쿼리만 늘어 다 같이 느려진다. 개선 묶음 뒤 풀 5에서 커넥션 대기는 0이었고, ISE-296에서도 시한 초과 0건이었다(ADR 0064).
- 원칙: 커넥션을 오래 쥐는 쿼리가 원인이면 풀이 아니라 쿼리를 고친다. 자동 배정 쿼리가 인덱스 없이 249만 행을 읽으며 785ms씩 커넥션을 쥐었을 때 인덱스로 고쳤다(TS-72).
- 약한 곳: 풀 10이 나쁘다는 근거는 1회 측정이다. 응모·추첨·접수형 소비자가 겹치는 조합은 재지 않았다.

## 4. 좌석 조회는 왜 서비스 메모리 캐시인가

- 지금: 바뀌지 않는 좌석 배치는 회차마다 한 번 만들어 서비스 메모리에, 좌석 상태는 1초 캐시.
- 대안: Redis 캐시(SA 원안), 캐시 없음.
- 근거: 같은 조건에서 Redis에 두자 요청마다 1.3MB를 옮겨 역직렬화하느라 p95가 7.0ms에서 38.3ms로, 건당 CPU가 약 4.5배가 됐다. 배치는 공연 중 바뀌지 않아 서버마다 따로 들고 있어도 어긋나지 않는다. 배포 서버에서 실패 없이 버틴 좌석 조회가 초당 5건에서 200건이 됐다.
- 대가: 서버를 여러 대로 늘리면 각자 캐시를 만든다(배치는 불변이라 정합성 문제는 없고 메모리만 더 든다). 남은 한계는 큰 응답(15,000석 약 820KB)을 만드는 CPU다.

## 5. 결제는 왜 SAGA 코레오그래피와 "결과 모름"인가

- 지금: 결제가 결과를 Outbox → Kafka로 내고 예매가 받아 확정·해제·환불 요청을 한다. PG 타임아웃은 실패가 아니라 UNKNOWN으로 두고 재조회한다.
- 대안: 예매 서비스가 조정자가 되는 오케스트레이션(AI 추천), 결제가 예매를 HTTP로 직접 호출, 타임아웃을 실패로 처리.
- 근거:
  - 참여 서비스가 둘뿐이라 결과 이벤트 구독으로 충분하다. 오케스트레이터는 상태를 하나 더 만든다.
  - HTTP 직접 호출이면 예매가 잠깐 죽어 있을 때 결과가 사라진다. Kafka에 두면 살아난 뒤 처리한다.
  - 타임아웃을 실패로 두면 "돈은 빠졌는데 표가 없는" 상태가 생긴다. 고객 피해가 가장 큰 경우다.
  - DB 커밋과 이벤트 발행을 Outbox로 묶어, 커밋 뒤 발행 직전에 죽어도 이벤트가 사라지지 않는다. 받는 쪽은 Inbox(`processed_events`)와 UNIQUE로 두 번 와도 한 번만 반영한다.
- 대가: Outbox 폴링 때문에 최대 500ms 발행 지연이 있다. 흐름이 서비스에 흩어져 추적(Zipkin)과 흐름도로 보완한다. TX1 커밋 응답이 유실되면 승인 없이 DECLINED(NOT_SENT)로 끝나는 한계를 받아들였다(ADR 0048). 이중 승인 위험보다 낫다고 판단했다.

## 6. Gateway는 왜 동시 처리 상한 64인가

- 지금: Gateway 맨 앞(HttpHandler)에서 동시 요청 64를 넘으면 즉시 503 + Retry-After.
- 대안: 메모리만 늘리기, 상한 500(구현 세션 제안)·128(6차 측정 안), 맨 앞 요청률 제한(AI 추천).
- 근거: 상한이 없을 때 Gateway가 768MiB에서 세 번 죽었고 메모리만 늘리면 더 느려졌다. 64는 리틀의 법칙(동시 요청 수 = 처리량 × 처리 시간)으로 계산했다. 상한 500 → 64로 2,000/s p95가 571ms에서 87ms로 줄고 성공 처리량이 1,304에서 1,696/s로 늘었다. AI가 권한 맨 앞 요청률 제한은 받지 않고 인증 차단기를 예민하게 하는 실험을 먼저 했지만 실패했고(TS-57), 그 뒤 동시 처리 상한을 넣었다. 요청률 제한은 값이 장비 성능에 묶인다는 점도 고려했다(ADR 0050).
- 대가: 큰 응답(좌석 조회)이 상한 자리를 오래 쥐면 서비스는 빠른데 Gateway가 503을 낸다(TS-77). 그래서 좌석 선점 비교 측정(ISE-296)은 Gateway 상한을 끄고 쟀다. 운영 값 상향(512 등)은 정하지 않았다.

## 7. 인프라는 왜 EC2 한 대인가

- 지금: EC2 m7i.xlarge 한 대에 컨테이너 약 20개, 메모리 상한 합계 장비의 86%.
- 대안: 처음부터 RDS·ElastiCache 분리, Kubernetes.
- 근거: 일정(4주)과 비용 안에서 전체 MSA를 재현 가능하게 띄우는 것이 목적이었다. 대신 운영 기본기를 갖췄다: 컨테이너별 메모리 상한과 G1 GC, healthcheck와 기동 순서, 커밋 SHA 이미지, 스모크 실패 시 자동 되돌림(실제로 한 번 동작), 알림.
- 대가: 장비 한 대가 단일 장애점이다. Kafka 복제도 1이다. 측정 결과의 절대값은 이 장비 기준이다. 발표에서 이 한계를 함께 말한다.

## 8. 성능 주장은 왜 믿을 만한가

- 수정하지 않은 코드에서 시작해 병목 하나씩 고치고, 측정 전에 예상을 적었다.
- 발생기 한계를 먼저 걸렀다: `dropped_iterations`, k6 메모리, 발생기 지연. k6 메모리 때문에 결론을 한 번 뒤집었고 그 정정을 기록했다(TS-69).
- 매회 대사 위반 0을 함께 확인했다. 빠르지만 틀린 결과는 쓰지 않는다.
- local 결론을 배포에서 다시 확인했고, 두 번 뒤집힌 사실을 숨기지 않았다(동시 처리 상한, 풀 크기).
- 약한 곳: 많은 배포 측정이 1회다. 발표 비교점(local base·F)만 3회다. 부하 측정은 Mock PG로만 했다.

## 면접 포인트

- "지금 설계에서 가장 자신 있는 결정은" → 좌석 경합의 최종 판정을 DB 조건부 UPDATE에 둔 것. 앞단 장치(대기열, 캐시 사전 거절, 잠금 50ms)는 줄을 짧게 할 뿐 정합성을 맡지 않아서, 어느 장치가 틀려도 중복 판매가 생기지 않는다. 모든 측정에서 대사 위반 0이다.
- "만들어 놓고 안 쓰는 기능이 있나" → 선점 동시 처리 상한과 접수형 선점. 둘 다 측정으로 비교한 뒤 지금 조건에서는 대가가 더 크다고 보고 끄거나 비교용으로 남겼다. 다시 켤 조건(커넥션 대기가 주 병목)을 ADR에 적어 두었다.
- "측정 결과를 어떻게 해석했나" → local과 배포가 다를 때 배포를 따랐다. local은 DB CPU가 넉넉해 운영의 CPU 포화를 재현하지 못한다.
