# 프로젝트가 지금 모습이 되기까지

목차: [README](README.md)

2026-10-26부터 11-19 발표까지 5명이 진행했다. 일정은 [`docs/core/milestones.md`](../../../core/milestones.md)를 따른다. 이 문서는 "언제 무엇을 했나"보다 "어디서 방향이 바뀌었고 왜 바뀌었나"를 남긴다. 결정 하나하나의 근거는 [06 결정 지도](06-decisions.md)에 있다.

## 1. 한눈에

| 기간 | 단계 | 한 일 | 커밋 수(대략) |
|---|---|---|---|
| ~10/26 | SA 1차·피드백 | AI 교차 검토, 튜터 피드백 28건 정리, SA v3·v3.1(결정 54건) | 15 |
| 10/27~10/29 | M1 공통·인증 | 패키지·공통 모듈·Config 서버 합의, 인증 반영, 계약(토큰·선점 결과) 확정 | 103 |
| 10/30~11/3 | M2 핵심 구현 | 선점·멱등·결제·Outbox·DLQ·추첨·프론트 대량 병합. 추첨을 Must로 올림 | 343 |
| 11/4~11/6 | M3 배포·MVP | 첫 배포(EC2 + GHCR + Jenkins), MVP 시연, k6 시나리오 | 242 |

| 11/13~11/16 | M4 후반 | 잠금 50ms, 접수형 소비자, 개선 묶음, 배포 선점 1차 측정 | 97 |

커밋은 11/2~11/4 사흘에 452개가 몰렸다. M2·M3 구현이 겹친 시기다.

## 2. 단계별 흐름

### 설계 (~10/26)

1. 10/23 SA 1차를 codex와 Claude가 따로 검토하고 결과를 합쳤다(`docs/sa-review/01-sa-1st-review.md`). 급한 문제로 세 가지가 나왔다: PG 타임아웃을 실패로 다룸, 발제 필수 항목이 마지막 주에 몰림, 좌석 상태 전이 규칙이 없음.
2. 같은 날 PG 타임아웃 처리 방식(`02-pg-timeout-handling.md`)과 좌석 선점 Kafka 설계(`03-seat-hold-kafka-design.md`)를 따로 조사했다.
3. 10/26 튜터 피드백 28건을 정리하고 반영안을 썼다(`04`, `05`). 저장소는 이날 에이전트 규칙과 판단 기록 체계부터 만들었다.

### M1 (10/27~10/29)

- 10/27 통합 회의로 SA v3.2: 패키지 `com.iseonjwa`, 공통 모듈 `common` 하나, Config 서버, Gradle, PostgreSQL 17, 브랜치 전략.
- 10/28 SA v3.3: 테이블 이름 복수형, ERD 5개, 역할 조정(결제 담당이 Mock PG까지, 추첨 담당 지정). 결제 ADR 0015~0028.
- 10/29~30 서비스 사이 계약 확정: 입장 토큰, 선점 결과(ADR 0032), 결제 토큰, 대기열 토큰 API(ADR 0031).

### M2 (10/30~11/3)

- 10/31 추첨 상세 설계(ADR 0036~0039).
- 11/2 팀 합의로 추첨을 Should에서 Must로 올렸다(`docs/core/milestones.md`, SA MASTER "11/2 바뀐 점").
- 11/2~3 선점 멱등, 추첨, Outbox·DLQ, 프론트를 병합했다. Flyway 버전 충돌 사고(TS-31: 두 PR이 같은 V5를 써 결제 테스트 268건 실패)가 이때 났다.

### M3 (11/4~11/6)

- 11/4 첫 배포. 스모크가 Eureka 갱신 대기 35초 때문에 503을 받아 재확인을 120초로 늘렸다(TS-34).
- 11/5 배포 장비를 m7i-flex에서 m7i로 바꿨다. 지속 부하에서 CPU가 보장되지 않아서다.
- 11/6 MVP 시연. 좌석 선점 동시성·k6 측정(#349)과 오픈 피크 k6 시나리오(#350)를 병합했다.

### 측정 기반 (11/7~11/12)

- local에서 좌석 선점 K1 단계 측정을 base부터 했다. 병목은 GC → 커넥션 대기 → DB 조인 → 직렬화 순서로 옮겨 갔다([04 부하 테스트](04-load-test.md) 3절).
- 배포 서버에서 Gateway 측정을 8차까지 했다. 인증 차단기, Gateway OOM, 동시 처리 상한, 거절 지점, 요청 로그가 차례로 문제였다.
- 11/11 예매 취소·환불이 들어갔다. 배포 자동 되돌림이 실제로 한 번 동작했다.
- 11/12 접수형 선점 접수 API(ISE-16), 결제 토큰 ES256(ADR 0055), 입장 토큰 소모 시점(ADR 0053)이 들어갔다.

### M4 후반 (11/13~11/16)

- 11/13 좌석 잠금 대기 50ms(ADR 0061), 선점 구조 개선 세 가지(ADR 0062). LLM 가상 사용자(Synthetic Data) 도입. 추첨 자동결제 10분 내 완료율 100%.
- 11/14 접수형 소비자·DLQ·30초 시한(ISE-17). 좌석 조회 P4c(1초 상태 캐시).
- 11/15 O1(섞인 흐름) 균일 대 Synthetic 비교. 응모를 동기 INSERT·201로 SA를 맞춤.
- 11/16 개선 묶음(1초 캐시 사전 거절, 직렬화 재사용, JIT 예열, 자동 배정 인덱스, 요청 로그 축소). 측정·시연 시드를 15,000석에서 1,500석으로 줄임(ADR 0060). 배포 선점 측정 1차.

### 발표 준비 (11/17~)

- 배포 선점 2차 측정으로 결론을 냈다. 선점 동시 처리 상한은 운영에서 끄고, 커넥션 풀은 5를 유지한다(ADR 0062 갱신, ADR 0064).
- 토스 결제 실패 때 Mock PG로 넘기는 처리, README 새로 쓰기(ISE-308), 발표 한 장 자료.

## 3. 방향이 바뀐 지점

| 주제 | 처음 안 | 바뀐 안 | 바꾼 이유 |
|---|---|---|---|
| 서비스 경계 | 5개(대기열·추첨 분리) | 3개 + reservation 안 모듈 | 추첨은 좌석과 한 트랜잭션이 필요. 대기열은 떼어 내도 장애가 격리되지 않음 |
| PG 타임아웃 | 실패로 처리 | UNKNOWN + 재조회, 만료 뒤 승인은 자동 환불 | 실패로 두면 "돈은 빠졌는데 표가 없는" 상태가 생김(AI 검토 C1) |
| SAGA | AI 추천은 오케스트레이션 | 코레오그래피 | 참여 서비스가 예매·결제 둘뿐 |
| 대기열 순번 | 진입 시각 ZSET | seq 카운터, `seq <= admitted` | 10/26 튜터 피드백 반영(`docs/sa-review/04-mentor-feedback-1026.md`) |
| 결제 토큰 | 공유 비밀 HMAC | ES256(개인키 서명, 공개키 검증) | 검증하는 결제 서비스가 토큰을 만들 수 없어야 함(ADR 0055) |
| 추첨 자동결제 PG 허가 | 일반 결제와 같은 그룹 | 전용 그룹 `pg-billing` 3, 소비자 3 | 측정에서 10분 완료율 92~93%, 일반 결제 503 9.5%(ADR 0051) |
| 응모 접수 | Kafka 접수(202) | 동기 INSERT(201) | 측정 p95 10.58ms로 바꿀 조건(300ms 초과)에 닿지 않음 |
| Gateway 과부하 | 상한 없음 | 동시 처리 상한 64 + 거절 앞당김 + 요청 로그 축소 | Gateway OOM 3회. 메모리만 늘리면 더 느려짐(TS-58) |
| 좌석 조회 | 엔티티 조회 | DTO → 배치 로컬 캐시 → 1초 상태 캐시 | 단계마다 측정으로 다음 병목 확인 |
| 좌석 잠금 대기 | 무한 → 500ms | 50ms | AI가 먼저 권한 SKIP LOCKED는 측정에서 성공이 83→56으로 줄어 거부 |
| 선점 동시 처리 상한 | 4로 켬(local 효과) | 운영에서는 끔 | 배포 측정에서 대가(503)만 보임 |
| 시드 규모 | 15,000석 | 1,500석 | 좌석 응답 하나가 약 830KB라 4코어를 응답 생성만으로 채웠다. 실제 공연장 값(SA 3-2)은 그대로 둔다(ADR 0060) |

## 4. 일하는 방식에서 바뀐 것

- 처음부터 "AI 판단 기록"을 남겼다. AI 제안을 받으면 수용·거부·보류와 근거를 `docs/ai-judgments/`에 쓴다. 발제 필수 "AI 설계 검증 로그"의 원천이다. 거부 사례를 모아 보면 대부분 "측정해 보니 다르다" 또는 "우리 조건(서비스 수, 장비 한 대)에서는 과하다"였다.
- 11/4부터 성능 주장은 측정으로만 하기로 했다. JUnit으로 부하를 흉내 내자는 AI 제안을 거부하고 k6로 다시 쟀다(`docs/ai-judgments/kwonwoo/2026-11-04-k6-over-junit-load-approximation.md`).
- local 결론을 배포에서 다시 확인했다. 두 번 뒤집혔다: Gateway 상한(TS-77), 선점 동시 처리 상한(ADR 0062 11/17 갱신). "내 노트북에서 좋았다"를 근거로 운영 설정을 바꾸지 않는다.
- 서비스 사이 접점(이벤트, 토큰, 내부 API, 공유 설정)을 바꿀 때는 Linear `contract` 이슈로 알렸다(`docs/guides/contract-issues.md`).

## 면접 포인트

- "프로젝트에서 가장 크게 방향을 바꾼 결정은" → 서비스 경계를 5개에서 3개로 줄인 것. 나누는 기준을 "도메인 이름"이 아니라 "한 트랜잭션에서 함께 바뀌는 데이터"와 "떼어 냈을 때 장애가 격리되는가"로 잡았다.
- "측정 결과가 예상과 달랐던 적은" → 선점 동시 처리 상한. local에서는 타임아웃을 0%로 만들었지만, 배포 장비에서는 커넥션 대기가 원래 문제가 아니어서 503만 늘렸다. 그래서 끄고 비상 스위치로 남겼다.
